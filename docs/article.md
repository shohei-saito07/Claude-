## はじめに

「AI駆動開発」という言葉をよく聞くようになりました。AI に「これ作って」と言ってコードを書いてもらうイメージはあるけれど、実際にどう進めれば学習につながるのかは、いまひとつピンと来ません。動画やデモを眺めていても「華やかな成果物」は流れてくる一方で、最初の一歩で何をすればいいのか、地味な部分の情報は意外と少ないように感じていました。

そこで本記事では、Claude Code を相棒にして、Python の小さな TODO CLI を一から立ち上げるまでの流れをそのまま記録しました。何を作るか決めるところから始まり、雛形を整え、TDD でテストと実装を一往復させ、`CLAUDE.md` でプロジェクトの作法を AI に渡し、最後に Pull Request を作ってマージするまでの体験を、できる限り端折らずに書き出しています。

「AI駆動開発を初めて触ってみたい」「TDD と AI を組み合わせてみたい」「Claude Code を実プロジェクトでどう使うか雰囲気を知りたい」という人の、最初の一歩のイメージになれば嬉しいです。

対象読者は、プログラミング経験が少しあり、Python の基本構文がなんとなく読める方を想定しています。フレームワークやテストの細かい知識は不要です。

## AI駆動開発とは何か

ざっくり言うと、**人間が「何を作るか・なぜ作るか」を決め、AI エージェントが「どう作るか」を担う開発スタイル** です。図にするとこんなイメージです。

```
人間 ──── 要求/意図 ────▶ AI
 ▲                         │
 │  成果物/質問             │
 └─────────────────────────┘
        ↓
  リポジトリ / CI / 実行環境
```

開発のループはこう回します。

```
1. 要件定義     人間: 何を/なぜ
2. 計画/設計    AI: 提案 → 人間: 承認
3. 実装         AI が編集
4. 検証         test/lint/型/動作確認
5. レビュー     人間が差分を確認
6. コミット     小さくマージ
```

役割分担はこんな感じになります。

| タスク | 人間 | AI |
| --- | --- | --- |
| 意思決定 | ◎ | △ |
| 要件定義 | ◎ | ○ |
| 実装 | △ | ◎ |
| テスト作成 | ○ | ◎ |
| レビュー | ◎ | ○ |

ポイントは「**AI が安全に動ける足場を先に整える**」こと。テスト・lint・型チェック・CI が揃っていればいるほど、AI の変更を機械的に検証できて、人間は意思決定に集中できます。逆に足場のないリポジトリで AI に丸投げすると、生成されたコードが正しいかどうかを毎回目視で確認するハメになり、結局スピードも品質も落ちます。最初の小さな投資が、その後の体験を大きく変える領域です。

もう一つ大事なのが「**会話を文書化する**」こと。Claude Code であれば `CLAUDE.md` に方針や禁止事項を書いておけば、AI が毎回それを踏まえて動いてくれます。「口頭で何度も同じことを言う」状態を防げるので、人間側の負荷も下がります。

## 何を作るか決める

最初に詰まりがちなのが「何を作ろう」です。学習用なら、**短期間で完成できて、開発ループを一周体験できる規模** がおすすめです。

筆者は AI に学習向けアイデアを 9 個出してもらい、その中から「TODO CLI」を選びました。理由は次の通りです。

- ファイル I/O・データ構造・テストの基礎が一通り入る
- 仕様がシンプルなので「AI駆動開発の流れ」自体に集中できる
- 後から「Web 化」「AI 連携」などに育てやすい

学習用プロジェクトでは、**派手さよりも「終わらせやすさ」** を優先するのがコツでした。

## なぜ Python を選んだか

言語は何でも良いのですが、AI 駆動開発の入門としては Python が素直です。

- 文法が短く、生成されたコードが読みやすい
- AI/LLM 関連ライブラリの大半が Python ファースト（`anthropic` SDK など）
- `pytest` と `ruff` という強力で軽量なテスト/lint 基盤がある
- パッケージ管理ツール `uv` が高速かつシンプル

TypeScript はフロント込みのフルスタック学習に強く、Go は速度や並行処理の学習に向いていますが、「AI と一緒にロジックを育てる体験」には Python が一番ハマる、というのが結論でした。

## プロジェクトの雛形を作る

ここからが実作業です。まずディレクトリ構成と設定ファイルを用意します。

```
todo-cli/
├── pyproject.toml
├── src/todo_cli/
│   ├── __init__.py
│   └── task_store.py
└── tests/
    └── test_task_store.py
```

`pyproject.toml` の中身は最小構成にしました。

```toml
[project]
name = "todo-cli"
version = "0.1.0"
requires-python = ">=3.11"

[project.scripts]
todo = "todo_cli.cli:main"

[dependency-groups]
dev = ["pytest>=8", "ruff>=0.6"]

[tool.pytest.ini_options]
testpaths = ["tests"]
addopts = "-q"

[tool.ruff]
line-length = 100
target-version = "py311"
[tool.ruff.lint]
select = ["E", "F", "I", "UP", "B"]
```

依存をインストールします。

```bash
uv sync
```

これだけで仮想環境が作られ、`pytest` と `ruff` が使えるようになります。`uv` は本当に速くて、待ち時間がほぼないのが気持ち良いです。

## TDD ループを 1 周回す

AI 駆動開発と TDD はとても相性が良いです。先にテストを書いておけば、AI が書いた実装が「ちゃんと意図通りか」を機械的に検証できます。

### Red: 失敗するテストを書く

`tests/test_task_store.py` に、まだ存在しない `TaskStore` のテストを書きます。

```python
from todo_cli.task_store import TaskStore


def test_new_store_is_empty():
    store = TaskStore()
    assert store.list() == []


def test_add_task_returns_task_with_id_and_title():
    store = TaskStore()
    task = store.add("買い物に行く")
    assert task.id == 1
    assert task.title == "買い物に行く"
    assert task.done is False


def test_complete_marks_task_done():
    store = TaskStore()
    task = store.add("掃除")
    store.complete(task.id)
    assert store.list()[0].done is True
```

この時点で `uv run pytest` を実行すると、当然「モジュールが見つからない」と怒られます。これが Red です。

### Green: 最小実装で通す

次に、テストが通る最小限の実装を入れます。

```python
from dataclasses import dataclass, field


@dataclass
class Task:
    id: int
    title: str
    done: bool = False


@dataclass
class TaskStore:
    _tasks: list[Task] = field(default_factory=list)
    _next_id: int = 1

    def add(self, title: str) -> Task:
        task = Task(id=self._next_id, title=title)
        self._tasks.append(task)
        self._next_id += 1
        return task

    def list(self) -> list[Task]:
        return list(self._tasks)

    def complete(self, task_id: int) -> None:
        for task in self._tasks:
            if task.id == task_id:
                task.done = True
                return
        raise KeyError(task_id)
```

再度テスト。

```bash
$ uv run pytest
.....                              [100%]
5 passed in 0.01s

$ uv run ruff check
All checks passed!
```

5 件全てグリーン、lint も通過。気持ちが良い瞬間です。

### Refactor

今回は実装が小さいので、追加の整理は省略しました。実務では「重複削除」「命名変更」「責務分離」をここで行います。重要なのは、**Refactor フェーズではテストを変えない** という点です。テストが変わらないまま実装だけが綺麗になっていく感覚は、TDD の気持ち良さの中核と言えます。

このループを意識的に回すと、AI に頼む粒度も自然と整います。「`add` で空文字列を弾けるようにして、対応するテストも追加してください」のように、Red を先に作って Green に向かう依頼を出せば、AI は迷わず動けますし、人間も差分の意味を読み解きやすくなります。

## CLAUDE.md でプロジェクトの「文化」を渡す

Claude Code はプロジェクト直下の `CLAUDE.md` を自動で読み込みます。ここに「このプロジェクトでの作法」を書いておくと、AI が毎回それを踏まえて作業してくれます。

```markdown
# Project: todo-cli

## スタック
- Python 3.11+ / uv / pytest / ruff

## 開発フロー（TDDループ）
1. tests/ に失敗するテストを追加（Red）
2. src/todo_cli/ に最小実装を入れて通す（Green）
3. 重複・命名・構造を整える（Refactor）

## AI への指示
- 新機能は必ず先にテストから書く
- パブリック API を変えたら関連テストも更新する
- ruff check と pytest が両方グリーンになるまで完了としない
- 仕様を勝手に拡張しない
```

`CLAUDE.md` は **「AI に渡すオンボーディング資料」** だと考えると分かりやすいです。新メンバーに最初に読んでもらう README と同じ役割を、AI に対して果たします。

## Pull Request を体験する

学習用なら個人開発でも、**PR を作る練習** はしておくと得です。差分が一覧で見えるので、AI が書いたコードを安全にレビューする場として理想的です。

### 流れ

```
ブランチ作成 → コミット → push → PR 作成 → レビュー → マージ → ブランチ削除
```

実際に作った PR では、

- **Conversation** タブで本文と議論
- **Commits** タブでコミット履歴
- **Files changed** タブで全差分（赤=削除/緑=追加）
- 任意の行に行コメントを付けられる
- **Approve / Request changes / Comment** から好きなレビュータイプを選べる

を一通り触りました。マージは **Squash and merge** を選択。複数コミットが 1 つに圧縮されて main の履歴がシンプルに保たれます。

おまけで、リポジトリに導入してあった ChatGPT の Codex がプルリクに自動レビューコメントをつけてくれました。**人間 + 複数 AI が同じ PR をレビューする** という体験は、まさに AI 駆動開発らしい光景でした。

### マージ後の片付け

```bash
git fetch origin --prune     # 削除されたリモートブランチを掃除
git rebase origin/main       # ローカルを最新に追従
```

これで次の開発ブランチを切る準備が整います。

学習用の個人開発であっても、PR を経由する習慣はつけておくと得です。理由は単純で、**自分のコードを「他人の目」で見る練習になる** からです。コミット直後の頭の熱が冷めた状態で差分を眺めると、変数名の違和感や、消し忘れの一行がはっきり見えてきます。AI 駆動開発ではコードが量産される分、こうした「冷静に見直す関所」を意図的に挟む価値はますます大きくなっていると感じました。

## 学んだこと・詰まったこと

実際に手を動かして気づいた点を残しておきます。

- **「AI に丸投げ」ではなく「AI と分担」が現実的**。要件と意思決定は人間が握り、実装と検証を AI に任せる。役割を分けると会話がブレない。
- **足場（テスト・lint）が先**。AI が安心して動ける環境を整える方が、結果的に速い。
- **CLAUDE.md は早めに書く**。書くこと自体が「自分のプロジェクトの方針」を言語化する作業になる。
- **小さく PR を区切る**。1 PR = 1 関心事にすると、AI に頼むときの指示も自然に粒度が揃う。
- **PR レビューが学習を加速する**。差分を眺めながら「自分でも書けるかな?」と読む時間が、一番手応えがあった。
- **詰まったときは「何を作るか」に立ち返る**。AI とのやり取りが迷子になりかけたら、目的に戻って指示を出し直すと、ほぼ確実に立て直せた。
- **Codex のような他の AI レビュアーと組み合わせるのも面白い**。別系統のモデルが指摘してくれるので、見落としに気づけるケースがあった。

学習という観点でいちばん効いたのは、**「AI に書いてもらったコードを自分で読み直す時間」** でした。実装そのものは AI が出してくれますが、それを差分として眺め、「なぜこの設計を選んだのか」を自分の中で言語化していくと、知識が定着していく感覚があります。AI 駆動開発は、コードを書く時間が減る代わりに、**読む時間と考える時間が増える** スタイルだと言っても良いかもしれません。

## 次にやりたいこと

このリポジトリは雛形まで完成したので、次はこのあたりに進めようと考えています。

- 機能ごとに小さな PR を切って、AI レビューを毎回挟む

## おわりに

AI 駆動開発と聞くと「魔法のように一発で動くものができる」イメージがありますが、実際の手触りは **「丁寧な共同作業」** に近いものでした。テストを書き、差分を読み、PR でレビューする。基本的なソフトウェア開発の作法はそのままで、その上に AI という強力なペアプロ相手が加わる、という感覚です。

学習を始めるハードルは思ったより低いので、興味があれば `uv` と `pytest` だけ入れて、空のリポジトリから一緒に始めてみてください。本記事と同じ手順を踏めば、半日かからずここまで辿り着けるはずです。慣れてきたら、CLI レイヤや永続化、外部 API との連携などに少しずつ手を広げていくと、学習が地続きにつながっていきます。

最後に強調しておきたいのは、**AI 駆動開発の中心にいるのは依然として人間** だということです。何を作るかを決め、テストで意図を表現し、PR で差分を確かめる。AI はそのどれもを助けてくれますが、舵を取るのは自分自身です。地味な手順を一つずつ踏んでいくほど、AI の出力も自分の理解も、安定して伸びていく実感があります。
